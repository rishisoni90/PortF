The one-liner
// how to explain it in 2 lines
"Built a platform at Ford where business teams type the rules for vehicle features into a website, and the backend automatically enforces, validates, and deploys those rules — replacing scattered spreadsheets and manual coordination across the entire organization."
The analogy

Think of it like McDonald's Menu Management

Before this platform existed, changing a vehicle feature rule was like calling every McDonald's franchise individually to say "add the McRib this month." It was manual, inconsistent, and error-prone across hundreds of teams.

🍟 The Analogy
"Instead of calling every franchise, McDonald's HQ has one system where they flip a switch — and every location updates instantly. I built that switch system for Ford's vehicle features."
Business teams go to a website (the Angular UI), type in their rules ("feature A can't exist without feature B in Market X"), hit save, and the platform takes care of enforcing it everywhere — no engineers needed, no spreadsheets, no manual calls.

The one-liner
// how to explain it in 2 lines
"Every international wire leaving Capital One travels through a SWIFT gateway — a server called SAA. Rotating SAA's password sounds simple, but first you have to safely shut down every terminal connected to it, or you break live wire flows. I automated that entire sequence with Ansible."
The analogy

Think of it like a Power Grid Maintenance Window

Imagine a city power grid. Before an electrician can replace the main transformer (SAA), they have to call every factory, hospital, and office connected to it and have them shut down their equipment — in the right order — so nothing blows up when the power is cut. Then they swap the transformer, restore power, and everything reconnects.

⚡ The Analogy
"SAA is the transformer. The Gateway LTs are the factories plugged into it. Before I change the password (replace the transformer), every Gateway LT has to be safely shut down. I built the Ansible playbook that calls every factory, shuts them down in order, swaps the credentials, then brings everything back online."
The "factories" are the Gateway LTs — terminals like LT-WIRE-01, LT-INTL-01 — through which Capital One's downstream systems send wire messages. If you change SAA's password while they're still running, their connections break mid-transaction. Real wires fail. My playbook eliminates that risk entirely.
The infrastructure

Three Components I Worked On

The SWIFT setup at Capital One has three main components — each playing a distinct role in how a wire gets from Capital One's system out to a bank across the world.

SAA
SWIFT Alliance Access — the main gateway server. All wire messages go through here. This is the one whose password gets rotated.
SNL
SWIFT Net Link — the secure tunnel to the SWIFT network. Think of it as the internet connection for SAA. Without SNL, no messages can leave.
SAG
SWIFT Alliance Gateway — the traffic router. Multiple internal systems connect to SAG, which routes their messages to the right SAA instance.

How it works — step by step

Walk Someone Through It

📋
Pre-flight: Check All Gateway LTs are in a Safe State
The Ansible playbook starts by inventorying all Gateway LTs connected to this SAA instance. It checks their current connection state. If any are mid-transaction or in an unexpected state, the playbook can pause or abort. Nothing proceeds until this check is clean.
Ansible inventory · connection state check
🔴
Shut Down Every Gateway LT — In the Right Order
The playbook issues a graceful shutdown to each LT in a defined sequence — not randomly, but in dependency order. It waits between each to confirm the disconnect was clean. This is the most critical phase: if any LT is still connected when the password changes, that terminal's connection breaks permanently until someone manually reconnects it.
⚠️ Most critical step — must be verified before rotation
🔑
Rotate the Password via CyberArk / HashiCorp Vault
With all terminals cleanly down, the playbook triggers credential rotation. A new password is generated and stored in CyberArk or HashiCorp Vault — the secret is never in the script as plaintext. SAA is updated with the new credential. The entire exchange happens in memory, with no credentials written to logs.
CyberArk · HashiCorp Vault · zero plaintext credentials
✅
Verify SAA Is Healthy Before Reconnecting Anything
Before bringing any LT back online, the playbook sends a health check to SAA using the new credential. It must respond with a 200 OK. If SAA fails to respond, the playbook halts and alerts — catching a failed rotation before any LT tries to reconnect with mismatched credentials.
Health check · retry logic
🔁
Bring Gateway LTs Back Up — In Reverse Order
The playbook restores each Gateway LT in reverse shutdown order, verifying each connection before moving to the next. Once all LTs report connected and healthy, the rotation is complete. Downstream wire systems never noticed anything happened — they just reconnected automatically.
Ordered restart · connectivity verification
📊
Audit Log Written — SWIFT CSP Compliance
The playbook writes a timestamped audit log: which LTs were cycled, the rotation outcome, and the Vault reference for the new credential. SWIFT's Customer Security Programme (CSP) requires banks to document credential rotation events. This log is that documentation — auto-generated, every time.
SWIFT CSP compliance · audit trail
