01 — Context

What Is SWIFT & Why It Matters at Capital One

SWIFT (Society for Worldwide Interbank Financial Telecommunication) is the global messaging network that banks use to send international wire transfers. When Capital One wires money internationally — millions of dollars per transaction — those payment instructions travel through the SWIFT network. Capital One must maintain certified infrastructure to stay connected to it.

Think of SWIFT as the postal backbone for international banking. The components I worked on are Capital One's "post office" — the ECS services and infrastructure that process every outgoing and incoming international wire before it reaches or leaves the bank.

🌐

Global Wire Network

SWIFT connects 11,000+ financial institutions across 200+ countries. Every international wire Capital One sends passes through this infrastructure.

🏛️

SWIFT CSP Compliance

SWIFT's Customer Security Programme mandates annual controls — including regular credential rotation on gateway systems. Non-compliance risks losing network access entirely.

☁️

ECS-Based Architecture

SAA runs as an ECS service on AWS — containerized, cloud-native. It connects to an Oracle database that stores all wire messages, audit logs, and transaction state.

03 — The Problem

Why SAA's Database Password Needs Rotation

SAA is an ECS service. It doesn't have a "login password" — what it has is a database password it uses to connect to its Oracle DB. Every wire message, audit trail entry, and transaction record gets written there. SWIFT CSP compliance requires this DB credential to be rotated on schedule.

// why this db credential is compliance-critical
📋
SWIFT CSP Requirement SWIFT audits Capital One annually. Rotating privileged DB credentials on gateway systems is a mandatory control. Failing it risks losing SWIFT network access — which means no international wires.
🗄️
SAA Writes Everything to This DB Wire messages, MT103/MT202 records, audit trails, settlement confirmations — all written to the Oracle DB via the SAA ECS service. This credential is the key to that entire audit record.
⏱️
Credential Age = Security Risk A DB password that hasn't changed in months may have been seen in a config backup, an old deployment artifact, or an engineer who has since left. Regular rotation limits the exposure window.
⚠️ Why You Can't Just Rotate Mid-Flight

SAA's ECS service is actively using that DB connection — constantly writing wire messages through connected Gateway LTs (Logical Terminals). If you rotate the Oracle DB password while SAA is mid-write, SAA's connection pool breaks. Active wire transactions fail. In a live banking system, a dropped wire record is a compliance exception and a potential financial loss. The DB password can only be safely rotated when SAA has no active DB writes in-flight — which means all Gateway LTs must be stopped first.

04 — The Ansible Playbook

The Correct Rotation Sequence

I built an Ansible playbook that executes the complete DB password rotation in the right order. The key principle: SAA must have zero active DB writes before the password changes. That means draining the Gateway LTs first.

📋
Step 1 — Pre-flight: Verify SAA ECS Task is Healthy
The playbook first confirms the SAA ECS service is running and in a stable state. It checks the Oracle DB connection is active and that SAA is not mid-task (e.g., processing a large batch of wire messages). If anything is unexpected, the playbook aborts before touching anything.
ECS task status check · DB connection health · pre-flight gate
🔴
Step 2 — Shut Down All Gateway LTs (In Order)
Gateway LTs (Logical Terminals) are the channel endpoints through which Capital One's downstream wire systems push messages into SAA. While any LT is active, SAA is potentially writing to the Oracle DB. The playbook shuts each LT down in a defined sequence — dependency order, with a verified disconnect between each. Once all LTs are down, SAA goes idle. No more active DB writes.
⚠️ Critical gate — SAA must be idle before DB password changes
Gateway LTs stopped per rotation run
LT-WIRE-01 LT-WIRE-02 LT-INTL-01 LT-INTL-02 + additional terminals
🔑
Step 3 — Rotate the Oracle DB Password via CyberArk / Vault
With all Gateway LTs stopped and SAA idle, the playbook triggers the Oracle DB password rotation. A new password is generated and stored in CyberArk or HashiCorp Vault. The Oracle DB user account for SAA is updated with the new credential. At no point is the password written to logs or stored in plain text in the script — it's always fetched directly from and written to the secret store.
CyberArk · HashiCorp Vault · Oracle DB user update · zero plaintext
🔄
Step 4 — Update SAA ECS Task with New DB Credential
The ECS task definition for SAA is updated to reference the new DB credential — either via an updated Secrets Manager reference or a direct environment variable change. The ECS service is then forced to redeploy, pulling the updated task definition. This ensures the running SAA container picks up the new Oracle password before any LTs reconnect.
ECS task definition update · forced redeployment · new credential injected
✅
Step 5 — Verify SAA ECS is Healthy with New DB Connection
Before any Gateway LT is brought back online, the playbook verifies that the redeployed SAA ECS task has successfully connected to Oracle with the new password. It checks that the DB connection pool is established and the service is in a healthy state. A failed DB connection here is caught before any LT tries to push wire messages — avoiding a scenario where LTs are up but SAA can't write.
ECS health check · Oracle DB connection verified · retry logic
🔁
Step 6 — Restart Gateway LTs in Reverse Order
With SAA healthy and connected to the updated Oracle DB, the playbook brings each Gateway LT back online in the reverse of the shutdown sequence. Each LT's connection is verified before the next one starts. Once all LTs are running and connected, wire processing resumes automatically — downstream systems reconnect without any manual intervention.
Ordered restart · reverse shutdown sequence · connectivity verified per LT
📊
Step 7 — Write Audit Log for SWIFT CSP Compliance
The playbook writes a timestamped audit record: which LTs were cycled, the rotation timestamp, the Vault/CyberArk reference for the new credential, and the ECS redeployment confirmation. This log is the compliance evidence for SWIFT CSP — auto-generated, consistent, and stored every time the rotation runs.
SWIFT CSP audit trail · auto-generated · timestamped

---
# SAA Oracle DB Password Rotation Playbook
# Capital One — SWIFT Infrastructure Team
# SAA runs as ECS service — DB password rotated via CyberArk/Vault
# Gateway LTs must be STOPPED before any DB credential change

- name: SAA Oracle DB Password Rotation
  hosts: swift_management_host
  gather_facts: yes
  vars:
    vault_path:        "secret/swift/saa/oracle_db"
    ecs_cluster:       "capital-one-swift-cluster"
    ecs_service:       "swift-saa-service"
    oracle_db_user:    "SAA_APP_USER"
    oracle_db_host:    "{{ lookup('env', 'ORACLE_HOST') }}"

  tasks:

    # ── PHASE 1: PRE-FLIGHT ────────────────────────────────────
    - name: Confirm SAA ECS service is stable before touching anything
      community.aws.ecs_service_info:
        cluster: "{{ ecs_cluster }}"
        service: "{{ ecs_service }}"
      register: ecs_info

    - name: Abort if SAA is not in steady state
      ansible.builtin.fail:
        msg: "SAA ECS not in STEADY_STATE — aborting rotation"
      when: ecs_info.services[0].deployments[0].rolloutState != 'COMPLETED'

    # ── PHASE 2: STOP ALL GATEWAY LTs ──────────────────────────
    - name: Stop Gateway LTs — ordered, verified per LT
      ansible.builtin.command:
        cmd: "/opt/swift/saa/bin/ltctl stop {{ item }}"
      loop: "{{ gateway_lts }}"
      loop_control:
        pause: 5   # 5s gap between each shutdown

    - name: Verify every LT is disconnected before proceeding
      ansible.builtin.command:
        cmd: "/opt/swift/saa/bin/ltctl status {{ item }}"
      loop: "{{ gateway_lts }}"
      failed_when: "'CONNECTED' in item_result.stdout"

    # ── PHASE 3: ROTATE ORACLE DB PASSWORD ─────────────────────
    - name: Generate new DB password and store in Vault
      community.hashi_vault.vault_write:
        path: "{{ vault_path }}"
        data:
          password:    "{{ lookup('password', '/dev/null length=32') }}"
          rotated_at:  "{{ ansible_date_time.iso8601 }}"
          rotated_by:  "ansible-automation"
      no_log: true   # never log credentials

    - name: Update Oracle DB user password
      community.oracle.oracle_sql:
        hostname:   "{{ oracle_db_host }}"
        sql:        "ALTER USER {{ oracle_db_user }} IDENTIFIED BY '{{ new_db_password }}'"
      no_log: true

    # ── PHASE 4: REDEPLOY SAA ECS WITH NEW CREDENTIAL ──────────
    - name: Force new ECS deployment — picks up updated DB secret
      community.aws.ecs_service:
        cluster:       "{{ ecs_cluster }}"
        name:          "{{ ecs_service }}"
        force_new_deployment: true
        state:         "present"

    - name: Wait for ECS redeployment to reach STEADY_STATE
      community.aws.ecs_service_info:
        cluster: "{{ ecs_cluster }}"
        service: "{{ ecs_service }}"
      register: ecs_post
      until:   "ecs_post.services[0].deployments[0].rolloutState == 'COMPLETED'"
      retries: 12
      delay:   15   # check every 15s, up to 3 minutes

    # ── PHASE 5: RESTART GATEWAY LTs ───────────────────────────
    - name: Restart Gateway LTs — reverse order
      ansible.builtin.command:
        cmd: "/opt/swift/saa/bin/ltctl start {{ item }}"
      loop: "{{ gateway_lts | reverse | list }}"
      loop_control:
        pause: 5

    # ── PHASE 6: AUDIT LOG ─────────────────────────────────────
    - name: Write SWIFT CSP compliance audit log
      ansible.builtin.lineinfile:
        path:  "/var/log/swift/db_rotation_audit.log"
        line:  "{{ ansible_date_time.iso8601 }} | DB_ROTATION_COMPLETE | user={{ oracle_db_user }} | lts_cycled={{ gateway_lts|length }} | vault={{ vault_path }}"

06 — AWS Migration

Migrating SWIFT Components to AWS

Alongside the password rotation work, I contributed to migrating SWIFT infrastructure from legacy on-premise environments to AWS — maintaining zero downtime on the live wire pipeline throughout.

☁️   Migration target: AWS ECS · EC2 Linux ARM64 · Oracle Instant Client · Java 17
EC2 + Oracle Setup
EC2 Instance Provisioning & Oracle Instant Client on ARM64

Provisioned EC2 instances for SWIFT components and installed the Oracle Instant Client on Linux ARM64 — required for the SAA ECS tasks to connect to Oracle databases. ARM64 has architecture-specific library paths that differ from x86, requiring careful configuration and testing before SWIFT components could successfully open DB connections.

S3 & IAM
Multi-Region S3 Buckets, Replication Rules & IAM Roles

Set up S3 buckets across dev and QA regions with replication rules and notification configurations — used for SWIFT config files and audit logs. Attached IAM roles with least-privilege policies to each component, ensuring SWIFT services access only what they need and nothing more.

Terraform
Lambda Security Groups Written in Terraform

Created and managed security groups for SWIFT-adjacent Lambda functions using Terraform — defining exactly which services the Lambdas can talk to. In financial infrastructure, security groups are the hard network boundary that ensures SWIFT traffic stays isolated from unrelated workloads.

Java 17 Migration
AWS Config File Updates & Runtime Upgrade

Updated AWS configuration files and migrated SAA's application runtime to Java 17. In a tightly version-coupled environment like SWIFT, a Java upgrade requires careful compatibility testing against SWIFT's own libraries before being promoted to production.

Production On-Call
On-call Production Support for the Live SWIFT Pipeline

Participated in on-call rotations for the live SWIFT wire pipeline — monitoring CloudWatch for anomalies, responding to alerts, and diagnosing issues in the wire flow. When wires involve real money, production support is not optional.

08 — Impact

Why This Work Mattered

SWIFT infrastructure work is invisible when it works — and catastrophic when it doesn't. The DB password rotation automation removed the most fragile manual process from the team's compliance workflow: a multi-step sequence, performed under pressure, on a live wire system, where a single mistake could break active transactions.

"SAA is an ECS service writing real wire transactions to an Oracle database in real time. Rotating that DB password safely meant stopping every Gateway LT first, rotating the credential via Vault, redeploying the ECS service, verifying the DB connection was healthy, then bringing everything back. I automated that entire sequence — so it runs the same way every time, without an engineer babysitting it at midnight."
