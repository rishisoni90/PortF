01 — Context

What Is SWIFT & Why It Matters

SWIFT (Society for Worldwide Interbank Financial Telecommunication) is the global messaging network that banks use to send international wire transfers. When Capital One wires money internationally — millions of dollars per transaction — those instructions travel through SWIFT. It's not just software. It's financial infrastructure subject to strict compliance, uptime, and security requirements.

Think of SWIFT as the postal system for international banking. The components I worked on are the Capital One "post office" — the servers and services that process every outgoing and incoming international wire before it leaves or enters the bank's systems.

🌐

Global Messaging Network

SWIFT connects 11,000+ financial institutions across 200+ countries. Every international wire transfer passes through it — including Capital One's.

🏛️

Regulated Infrastructure

SWIFT compliance is mandated. Downtime during a live wire, or a misconfigured credential, can cause real financial and legal consequences.

🔒

Security-First by Design

Password rotation, access controls, and audit trails aren't optional — they're SWIFT's Customer Security Programme (CSP) requirements that Capital One must meet annually.

02 — Architecture

The Three SWIFT Components

The SWIFT infrastructure at Capital One was organized around three core components, each handling a distinct role in the wire flow. Understanding all three was essential before I could safely automate anything.

// swift component architecture — capital one
SAA
SWIFT Alliance Access
The primary gateway — the actual server that connects Capital One to the SWIFT network. All outgoing and incoming wire messages pass through SAA. It authenticates with SWIFT, formats messages (MT103, MT202), and routes them. This is the most critical component — and the one whose password I automated rotating.
Gateway Server · Primary
SNL
SWIFT Net Link
The network connectivity layer. SNL is the service that maintains the secure tunnel between Capital One and the SWIFT network itself. If SNL is down, SAA cannot reach SWIFT — no messages can be sent or received. It's the pipe that SAA talks through.
Network Layer · Connectivity
SAG
SWIFT Alliance Gateway
The traffic router. SAG sits between internal Capital One systems (like the wire initiation apps) and SAA, routing message traffic intelligently. Multiple internal systems can connect to SAG, which manages which messages go to which SAA instance. It also handles load balancing and message queuing.
Traffic Router · Load Balancer

03 — The Problem

The Password Rotation Challenge

SAA — the primary SWIFT gateway — requires regular credential rotation as part of SWIFT's Customer Security Programme (CSP) compliance. This sounds simple. It wasn't.

⚠️ Why This Was High-Stakes

SAA doesn't just accept a new password in isolation. It's connected to multiple Gateway LTs (Logical Terminals) — the channel endpoints that downstream applications use to send wire messages. If you change the SAA password while any Gateway LT is still active and connected, those connections break mid-transaction. In a live banking environment, this means wires can fail, get stuck, or generate compliance exceptions. Every Gateway LT had to be safely shut down first.

Before I built the automation, this was a manual process — an engineer would have to:

😓 Before — Manual Process
  • 🔴   Manually log into each Gateway LT
  • 🔴   Shut each one down individually, in order
  • 🔴   Verify each was cleanly disconnected
  • 🔴   Then change the SAA password manually
  • 🔴   Bring each Gateway LT back up one by one
  • 🔴   Human error risk at every step — during production hours
✅ After — Ansible Automation
  • 🟢   Ansible playbook executes the full sequence
  • 🟢   All Gateway LTs shut down in correct order
  • 🟢   Connection state verified before proceeding
  • 🟢   Password rotated via CyberArk / HashiCorp Vault
  • 🟢   Gateway LTs brought back up and verified
  • 🟢   Zero human error — same script every time
04 — The Ansible Playbook

How I Automated It

I designed and built an Ansible playbook that automated the entire SAA password rotation sequence — including the pre-rotation Gateway LT shutdown and post-rotation verification. The key principle: nothing happens unless the previous step was clean.

📋
Step 1 — Inventory & Pre-flight Check
The playbook starts by loading the list of all Gateway LTs (Logical Terminals) connected to the SAA instance — the active channels through which downstream systems are sending wire messages. It checks their current state before proceeding. If any are mid-transaction, the playbook can be configured to wait or abort.
Ansible inventory · pre-flight validation
🔴
Step 2 — Shut Down All Gateway LTs (In Order)
This is the most critical step. The playbook shuts down each Gateway LT in a defined sequence — not all at once, but in the correct dependency order. Each LT disconnect is confirmed before moving to the next. This ensures no open connections remain to SAA before the password changes. Rushing this step is what breaks wires.
⚠️ Critical — must complete before password change
Gateway LTs disconnected per run
LT-WIRE-01 LT-WIRE-02 LT-INTL-01 LT-INTL-02 + additional terminals
🔑
Step 3 — Rotate the SAA Password via CyberArk / Vault
With all Gateway LTs cleanly disconnected, the playbook triggers the credential rotation. The new password is generated and stored in CyberArk (or HashiCorp Vault, depending on environment). The SAA instance is updated with the new credential. At no point does the password exist in plain text in the script — it's always fetched from and written to the secret store.
CyberArk · HashiCorp Vault · zero plaintext credentials
✅
Step 4 — Verify SAA is Healthy with New Credential
Before bringing any Gateway LTs back, the playbook verifies that SAA accepted the new password and is in a healthy state. A failed rotation here would be caught before reconnecting terminals — preventing LTs from coming up with mismatched credentials.
Health check · connection validation
🔁
Step 5 — Bring Gateway LTs Back Up
The playbook restores each Gateway LT in the correct order — the reverse of how they were shut down — verifying connectivity at each step. Once all LTs are back and reporting healthy, the rotation is complete. Downstream wire systems are automatically reconnected without any manual intervention.
Ordered restart · connectivity verification
📊
Step 6 — Audit Log & Notification
The playbook generates an audit trail of the rotation event — timestamps, which LTs were cycled, the rotation outcome, and the new credential reference in Vault/CyberArk. This log is critical for SWIFT CSP compliance reporting.
Audit trail · compliance log · SWIFT CSP
rotate_saa_password.yml Ansible Playbook (simplified) 
---
# SWIFT SAA Password Rotation Playbook
# Capital One — SWIFT Infrastructure Team
# Requires: all Gateway LTs cleanly shut down before password change

- name: SWIFT SAA Password Rotation
  hosts: swift_saa_servers
  gather_facts: yes
  vars:
    vault_path: "secret/swift/saa"
    cyberark_account: "SWIFT_SAA_PROD"
    rotation_window: "maintenance"

  tasks:

    # PHASE 1: PRE-FLIGHT VALIDATION
    - name: Verify SAA service is running
      ansible.builtin.service_facts:
      register: service_state

    - name: Fail if SAA is not in expected state
      ansible.builtin.fail:
        msg: "SAA not in running state — aborting rotation"
      when: service_state.ansible_facts.services['saa'].state != 'running'

    # PHASE 2: SHUT DOWN ALL GATEWAY LTs (in order)
    - name: Shut down Gateway LTs — ordered sequence
      ansible.builtin.command:
        cmd: "/opt/swift/saa/bin/ltctl stop {{ item }}"
      loop: "{{ gateway_lts }}"
      loop_control:
        pause: 5  # wait 5s between each shutdown
      register: lt_shutdown_results

    - name: Verify all LTs are disconnected
      ansible.builtin.command:
        cmd: "/opt/swift/saa/bin/ltctl status {{ item }}"
      loop: "{{ gateway_lts }}"
      register: lt_status
      failed_when: "'CONNECTED' in lt_status.stdout"  # abort if any still connected

    # PHASE 3: ROTATE PASSWORD VIA CYBERARK/VAULT
    - name: Generate new password and store in CyberArk
      community.hashi_vault.vault_write:
        path: "{{ vault_path }}"
        data:
          password: "{{ lookup('password', '/dev/null length=24 chars=ascii_letters,digits') }}"
          rotated_at: "{{ ansible_date_time.iso8601 }}"
      register: vault_write_result
      no_log: true  # never log credentials

    - name: Update SAA with new credential
      ansible.builtin.command:
        cmd: "/opt/swift/saa/bin/saapasswd -u saa_admin -p '{{ new_password }}'"
      no_log: true  # credential never written to logs

    # PHASE 4: VERIFY & RESTART GATEWAY LTs
    - name: Verify SAA health with new password
      ansible.builtin.uri:
        url: "https://{{ saa_host }}:8443/api/health"
        status_code: 200
      retries: 3
      delay: 10

    - name: Restart Gateway LTs in reverse order
      ansible.builtin.command:
        cmd: "/opt/swift/saa/bin/ltctl start {{ item }}"
      loop: "{{ gateway_lts | reverse | list }}"
      loop_control:
        pause: 5

    # PHASE 5: AUDIT LOG
    - name: Write rotation audit log
      ansible.builtin.lineinfile:
        path: "/var/log/swift/rotation_audit.log"
        line: "{{ ansible_date_time.iso8601 }} | ROTATION_COMPLETE | LTs={{ gateway_lts | length }} | Vault={{ vault_path }}"
05 — AWS Migration

Migrating SWIFT Components to AWS

In addition to the password rotation work, I contributed to the migration of SWIFT components onto AWS — moving from legacy on-premise infrastructure to a cloud-native, more resilient deployment model while maintaining zero downtime on the live wire pipeline.

☁️   Migration target: AWS EC2 · Linux ARM64 · Oracle Instant Client
AWS Environment Setup
EC2 Instance Provisioning & Oracle Instant Client

Worked on provisioning EC2 instances for the SWIFT components, including installing and configuring the Oracle Instant Client for Linux ARM64 on EC2 — required for the SWIFT components to connect to Oracle databases. ARM64 has architecture-specific library requirements that differ from x86, requiring careful configuration.

S3 & IAM Configuration
Multi-Region S3 Buckets with Replication Rules

Set up S3 buckets for different regions — dev and QA environments — configuring replication rules, notification rules, and attaching IAM roles. Cross-region replication ensures SWIFT logs and config files are backed up and available even if a regional outage occurs.

Terraform & Security Groups
Lambda Security Groups Written in Terraform

Created and managed Lambda Security Groups using Terraform — defining inbound/outbound rules that control what the SWIFT-connected Lambdas can communicate with. In a financial infrastructure context, security groups act as the firewall layer ensuring SWIFT traffic is isolated and controlled.

Java Version Migration
AWS Config File Updates & Java 17 Upgrade

Updated AWS configuration files and migrated the application runtime from an older Java version to Java 17 — a non-trivial change in an infrastructure where components are tightly version-coupled. Involved testing compatibility with SWIFT's own libraries and dependencies before promoting to production environments.

Production Support
On-call Production Support for SWIFT Pipeline

Participated in on-call production support rotations for the live SWIFT wire pipeline — monitoring CloudWatch for anomalies, responding to alerts, and diagnosing issues in the wire flow. When wires are real money, production support is not optional.
